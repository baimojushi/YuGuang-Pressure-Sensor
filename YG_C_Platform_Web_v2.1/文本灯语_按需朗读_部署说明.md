# 余光 V2.1：发送者文本灯语与按需朗读（服务 19）

> 版本：2026-10-31。基线为 `YG_C_Platform_Web_v2.1_siid19.zip`，与业务板 A 同步交付。源代码实现了平台业务、有限灯语 JSON 与业务板设备方法，**真实灵机云适配服务和实机验证仍需部署完成**。

## 1. 已实现的用户链路

1. 发送者输入不超过 140 字的文本，可在 H5 中点“按文字预览灯语”。`POST /api/light/preview` 按语义生成受控灯语，记录短期预览快照与生成依据。有效期十分钟；修改文字/意图/偏好后须重新预览。
2. `POST /api/messages` 创建消息时立即完成文本→灯语映射，持久化：`note`、`light`、`lightMapping`（版本、映射引擎、时间）、`message.id` 和事件日志 `lightEvents`。若发送者带来有效的 `previewId`，复用预览灯效，不重新推断。
3. 设备在非专注、非休息、灯光可显示时经 `GET /api/hardware/{deviceId}/pending` 获取排队指令与保存的灯效快照。平台只在设备真实确认显示后调用 `POST /api/hardware/{deviceId}/delivered` 并记录 `delivered` 事件。未显示的消息不会自动标成已送达。
4. 业务板 `care.present` 收到可信云适配器下发的 `light` 后才驱动 WS2812，校验 JSON 格式、低亮度约束、节奏与时间窗。仅实际显示且 GPIO5 在窗口内检测到高电平时，才提交“收到了”的持久回执；不自动朗读。
5. 用户主动说“余光，朗读刚才收到的消息”：A 板最终识别事件匹配朗读意图，经 `care.readRequested` 上传，云端可信适配器验证设备身份并为 Web 桥接签名。Web 校验配对、设备归属、消息已送达后，返回 `care.readText` 任务，A 板调用现有语音合成播放 API，并在播放结束/失败时 `care.readPlayed` 上报。
6. H5 还提供 HTTPS 浏览器语音识别→授权文本→浏览器语音朗读的独立体验路径。浏览器支持度受设备、浏览器与麦克风权限影响；它不代表业务板扬声器已通过实机验证。

## 2. 文本映射协议

```json
{
  "schema":"yuguang.light.v1",
  "pattern":"soft_pulse",
  "colors":["#E8A568","#FFF0D5"],
  "periodMs":2800,
  "cycles":2,
  "durationMs":5600,
  "maxBrightness":0.12,
  "description":"暖橙与乳白，低亮度交织",
  "sound":false,
  "vibration":false,
  "autoFade":true
}
```

四个预设语义为 `miss`（想念，柔桃粉慢起伏）、`meal`（吃饭，暖橙+乳白）、`rest`（休息，暖橙渐隐）、`cheer`（加油，两次柔和跃动）。未知表达回退到发送者所选意图。可选的私有模型只允许输出 `{"intent":"miss|meal|rest|cheer"}` 中的一个合法取值，模型不可下发自定义电平、闪烁、任意 RGB 或固件命令。

## 3. 需要配置的服务端环境变量

```bash
# 本机 Web App 服务或 Cloudflare/Supabase 服务端环境（绝不可写入网页）
VOICE_READ_BRIDGE_SECRET=<独立生成的至少32字符随机密钥>
CARE_ACK_BRIDGE_SECRET=<另一个独立随机密钥>
# 可选私有模型映射（不配置时直接使用可复现的本地规则引擎）
LIGHT_MAPPER_URL=https://your-private-model.example.com/classify
LIGHT_MAPPER_TOKEN=<私有模型访问令牌>
```

`server.js` 已透传以上环境变量；Cloudflare 环境通过服务绑定注入。私有模型接收发送者文本，正式启用前应取得用户知情授权并验证数据留存政策。不可将密钥放进前端或 Git 仓库。

## 4. 必须实现的灵机云双向适配器契约

真实厂商 MQTT 订阅/上报所需凭据、Topic 格式和云端签名格式没有得到厂商授权资料，因此**此交付不包含可直接上线的厂商适配器**。请在已有受信任云网关内完成下列动作：

- Web → A：认证后获取 `pending.command`，仅在可显示窗口下发 `care.present`，参数包含 `message_id`、`device_id`、`window_ms`、整个 `light` JSON。设备实际成功显示后回调 Web `/delivered`，失败则不标送达。
- A → Web：接收 `care/readRequested`（最终 ASR 文本；厂商云回调已完成设备身份鉴权），**由可信适配器**填充设备 ID、UUID、毫秒时间戳；使用独立 HMAC 密钥请求 `POST /api/bridge/voice-read`，带 `x-yg-timestamp-ms`、`x-yg-signature`（按照 `shared/care-ack.mjs` 的签名格式）。不得相信端侧 JSON 中自己声明的设备身份。
- Web → A：如果 Web 返回 `downlink.play===true`，下发 `care.readText`，参数使用 `downlink.params` 中的 `request_id/message_id/device_id/text`。因为重试会返回同一个请求 ID，A 板需保持重复请求不重复播放。
- A → Web：收到 `care/readPlayed` 事件后，适配器以独立签名请求 `POST /api/bridge/voice-playback`，记录真正 `played` / `failed` 结果。普通 MQTT 发送成功、HTTP 2xx 或 TTS 合成开始都不表示播放完成。
- A ↔ Web：GPIO5 回执继续使用已有的 `/api/bridge/care-ack` 与 `care.ackCommitted` 路径，并完成显示窗口/消息 ID 对应验证。
- 一次 `care.present` 只能消费一个消息 ID。平台原有同类型消息合并队列可能含多个 `messageIds`，生产适配器需要执行单条拆分或进行多消息事务协议升级；联调前不可默默只确认第一条却把其他消息标为已收到。

## 5. 本机回归

```bash
cd webapp
npm ci
npm run sync:hosting
npm run check:sync
npm test
```

运行当前环境不含 `express` 依赖时，可先执行 `node --test tests/*.test.js` 中可执行的非 HTTP 测试。ESP32-S3 使用 ESP-IDF 5.4.1 + 原厂依赖构建（必须确保 Xtensa 编译工具链可用）。

## 6. 未验收事项

- 真正厂商云网关身份鉴权、消息上行/下行推送、签名与重试、设备显示完成事件。
- 实机 ESP32-S3 编译、语音前端（VB701N）、语音合成发声及耳机/扬声器资源冲突。
- Cloudflare 和 Supabase 正式部署构建、浏览器端麦克风兼容性。
- 多条同类消息合并显示时的逐条确认语义、缺少网络时的设备离线恢复、长时压力与资源占用。

**验收标准：** 映射生成时间与实际展示时间分别记录；亲友原文只能由所属用户主动发起朗读；全链路任何阶段失败均不能伪报“已播放”。
